# Plan: MCP adoption phase 2 — measure first, then ship, then instrument

Status: v2 — REVISED after adversarial review (2 independent reviewers; changelog at
bottom). Supersedes v1, which had the ship/measure order inverted and a blocker in the
resource design.
Follows: the phase-1 adoption audit (PR #162 here, PR #648 in optionsahoy_web — both
open, green, UNMERGED).

## Context and the two facts that reshape it

- Live stats: `totalCalls` 68,119 but real tool calls are ~1,100 ALL-TIME (~98% of
  logged rows are handshakes/`tools/list`/crawlers/smoke). Real volume is tens of tool
  calls per week. Consequences: every metric must be scoped to actual tool calls, alert
  thresholds must be volume-conditioned, and ACQUISITION (new connections) likely
  outranks conversion tuning.
- Coverage truth: `coveredTickers()` returns 91 symbols, but 26 have null 5y AND 10y
  returns (recent IPOs) and resolve NOTHING for growth. Real quadrants: 61 growth+vol,
  3 growth-only (VRHI, RIME, VEEA), 24 vol-only, 2 neither (HAWK, FUSE). The live
  descriptions/instructions overclaim ("about 90 resolve growth"); phase 4 fixes this
  from a single computed source.

## Phase 1 — Routing eval harness FIRST (this repo; no deploy dependencies; ~3-4 h)

Build the instrument before shipping the change, so phase-1's description edits are
A/B'd with evidence instead of measured as a mystery later.

- `scripts/eval/routing-cases.json`, frozen and versioned (`casesVersion` field;
  append-only). 150-300 cases (at 60, the 95% CI is ~±8pp and any regression rule sits
  inside noise; marginal cost of more cases is trivial under prompt caching). Four
  kinds, REPORTED SEPARATELY (never one blended aggregate — a blended score rewards a
  description set that suppresses calls):
  1. single-tool utterances — include paraphrases generated by a DIFFERENT model from
     intent specs (not from the descriptions), to blunt teaching-to-the-test;
  2. ambiguous ISO-vs-NSO — graded correct only if the text response asks a clarifying
     question that names the ISO/NSO distinction (mere tool-call absence is NOT a pass);
  3. off-domain negatives — expect no tool call;
  4. multi-tool — first call must be in the allowed set.
- `scripts/eval-routing.mts` (tsx; add `@anthropic-ai/sdk` to devDependencies — not
  currently present; `files` ships only `dist`, so consumers unaffected):
  - tools + server instructions assembled from canonical `TOOLS`/`mcp.ts` (verified
    importable under plain tsx — no Cloudflare globals at module scope);
  - model MATRIX, not one model: default `claude-haiku-4-5` + the current claude.ai
    default (Sonnet-class), exact model IDs recorded; baselines are per-model and never
    compared across models;
  - temperature 0; `--trials N` for majority vote on close calls;
  - prompt caching on the shared tools+system prefix (comfortably over the 4096-token
    caching minimum; est. $0.10-0.30/run cached per model);
  - comparisons are PAIRED per-case: output the flipped-case list + per-kind rates +
    bootstrap CI over cases; flag only when the CI on the paired difference excludes 0;
  - appends {gitSha, model, casesVersion, perKindRates, flippedCases} as a JSON line to
    `scripts/eval/results.jsonl` (NEW pattern for this repo — the bench-append idiom
    lives in the app repo, not here);
  - `--toolspec <path>` + `--instructions <path>` to evaluate an alternate surface.
- Cheap CI-safe drift guard (vitest, no API): every case's expected tool name exists in
  `TOOLS` — catches dataset rot on rename/add.
- NOT in CI otherwise (API key, cost, stochastic margins).

## Phase 5 — Tool-scoped stats + weekly digest routine (~2-3 h)

5a. Stats extension (this repo). All new fields scoped to REAL tool calls
    (`endpoint = 'mcp:tools/call'` + REST calc endpoints) and EXCLUDING infra clients —
    `isInfraClient` currently filters only `mcp_samples`, never `mcp_calls`, and
    `.github/workflows/smoke.yml` hits the live endpoint on every main push plus a
    daily cron, so unscoped fields would count our own smoke:
    - `toolCalls7d`, `perDay14` [{day, toolCalls, toolErrors}], `topTools7d`
      (WINDOWED — the existing `topTools` is all-time and unusable for WoW mix),
    - `errorRate7d` = tool-call errors / tool calls,
    - `topErrorFields7d`: extracted from the stored `error_msg` (schema verified:
      `is_error`, `error_msg TEXT` truncated at 500) by matching the literal
      `field "<name>" required` prefix, then filtering `<name>` against a hard
      allowlist enumerated from the tool input schemas. Anything not exactly
      allowlisted is DROPPED (never truncated-and-included). Test with a poisoned
      fixture message. Update the stats.ts "PII-safe" header comment, and note the D1
      mock matches SQL by regex — each new query needs a new pattern in `mockDb()`.
5b. Digest routine (optionsahoy_web; deployed automatically by the reconciler):
    - `automation/routines/mcp-usage-digest.md` with FULL frontmatter (name, cron
      5-field UTC, model, environment_id, repo, allowed_tools, empty trigger_id —
      buildDesiredConfig hard-requires all of them) + `_stubs/mcp-usage-digest-stub.md`
      + manifest entry `""` -> the weekly local reconciler creates it and writes the id
      back via auto-PR.
    - Each run: fetch `/api/v1/stats` (public, no secret); read
      `automation/mcp-usage/latest.json`; compute WoW on TOOL-scoped fields; write
      dated snapshot + `latest.json` direct to main (etl-status dated+latest pattern —
      and phase 3 seeds BOTH files, so the first run never dereferences a missing
      latest.json); print the digest (the phone update), annotated with any
      `deploys.json` markers in the window.
    - Volume-conditioned escalation (raw WoW ratios false-alarm at Poisson-level
      volume): apply ratio rules only when prior week >= 30 tool calls, else compare
      against a 4-week trailing mean; error-rate rule additionally requires >= 5
      absolute errors. Escalate via the self-cleaning tracker pattern.

## P2 A/B results (2026-07-19) — run, and what it revealed

Ran the harness in `--via-claude-code` mode, old surface (pre-audit `main`, sha
f6fd292) vs new (audit branch chore/mcp-adoption-audit-2026-07-18, sha a522f5f),
paired n=200, dataset casesVersion 2026-07-19.1.

**Sonnet, paired (the merge-safety question):**
- single 98.6% -> 98.6% (0.0pp); ambiguous 100 -> 100; negative 80 -> 84 (+4pp,
  n=25, noise); multi 100 -> 100. 9 flips (5 new / 4 old), McNemar p=1.000.
- Verdict: **no regression.** The phase-1 changes are safe to merge (PR #162).

**Haiku, new arm (old arm killed mid-run, but the point was made):**
- 100% on every kind.

**The finding that matters more than the numbers:** the eval SATURATES and
cannot measure the audit's routing value on Claude-tier models. Root cause:
`called=2/200` — in claude -p mode with input-light utterances, the model almost
never emits a real tool_use; it asks for the tool's required inputs first
(correct STRICT_INPUT_NOTE behavior). So the eval measures tool IDENTIFICATION
from a reply, an easy task both surfaces pass at ~99-100%. There is no headroom
to detect a description improvement.

Implication (reinforces review finding #10, acquisition > conversion): on
capable routers, OptionsAhoy's tools are already selected correctly regardless
of description polish. The audit's value lives where this eval does not look:
correct USAGE once selected (input handling), weaker/older models, and new-user
acquisition.

**To make the eval discriminating (harness follow-up, not blocking the merge):**
1. Input-complete case variants: utterances that already carry the required
   fields, so the model CALLS the tool (called-route dominates) and we measure
   real tool_use selection among confusable tools -- where descriptions bite.
2. Raw-API mode (needs credentials): sees tool_use directly, no judge for
   called cases, exact surface control.
3. Harder confusables: cases engineered so two tools genuinely compete
   (ISO-vs-NSO partial signals, concentration-vs-put boundary).

**Decision:** merge PR #162 (safe per the gate) and cut v1.9.8; treat the
input-complete eval variants as the next harness iteration. Do NOT keep tuning
descriptions for routing on the strength of this eval -- it shows routing is not
the bottleneck. Redirect to the distribution/acquisition track.
